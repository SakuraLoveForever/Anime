# 离线模式本地账号设计

- 日期：2026-09-03
- 状态：待审阅
- 目标：让自部署的离线模式可以在同一台电脑上注册、登录和切换多个账号，并隔离每个账号的数据。

## 背景

当前项目有两条数据路径：

1. 配置 Supabase 时，`js/supabase.js` 负责登录、会话和云端数据同步。
2. 未配置 Supabase 时，番剧等数据保存在浏览器 `localStorage` 的 `offline_*` 键中，但登录按钮会被禁用；现有的“记住账号”逻辑也只适用于 Supabase。

本需求只要求同一台电脑上的本地账号，不要求跨设备同步，也不要求把离线账号接入 Supabase。

## 目标

- Supabase 未配置时，离线模式也能使用登录、注册、退出和切换账号。
- 不同本地账号的番剧、收藏夹、搜索源、搜索记录和 AI 设置互相隔离。
- 保留现有在线模式的行为：配置 Supabase 后仍使用 Supabase Auth 和云端数据。
- 第一次登录时尽量保留现有匿名离线数据。
- 用户只需在界面操作，不需要创建数据库、修改 SQL 或配置额外服务。
- 本地账号密码不保存为明文，也不再用 Base64 伪装密码。

## 非目标

- 不提供跨电脑、跨浏览器的数据同步。
- 不把本地账号同步到 Supabase。
- 不实现找回密码、邮箱验证、管理员后台或多用户权限管理。
- 不把本地账号当作高安全等级的服务器认证。拥有该浏览器用户数据访问权限的人仍可能读取或删除本地数据。

## 方案选择

### 方案 A：浏览器本地账号（推荐）

账号和数据全部放在当前浏览器的 `localStorage` 中，账号 ID 生成随机 UUID，数据键按账号 ID 加前缀。密码使用 Web Crypto PBKDF2 + 随机 salt 生成哈希，只保存哈希和 salt。

优点是无需新增后端、数据库或安装步骤，最符合“同一台电脑、离线、自部署”的需求；缺点是数据跟随浏览器配置文件，清除站点数据后无法恢复。

### 方案 B：Node.js 服务端 JSON 账号库

在 Node.js 服务端新增用户文件、密码哈希、会话 token 及按用户存储的数据接口。

该方案可以支持同一服务的多个浏览器，但会增加服务端状态、并发写入、会话安全、备份和迁移问题。对于当前需求属于不必要的复杂度。

### 方案 C：自部署 Supabase

使用 Docker 或独立 Supabase 实例提供 Auth 和数据库。

功能完整，但会重新引入数据库部署和维护成本，不符合本次“精简使用方式”的目标。

本设计采用方案 A。

## 数据模型

新增一个独立的本地认证模块，例如 `js/local-auth.js`，对页面提供注册、登录、注销和当前用户查询能力。

### 账号索引

全局保存于 `anime_local_users`：

```json
[
  {
    "id": "随机 UUID",
    "username": "alice",
    "normalizedUsername": "alice",
    "passwordSalt": "Base64 salt",
    "passwordHash": "Base64 PBKDF2 hash",
    "createdAt": "ISO 时间",
    "lastLoginAt": "ISO 时间"
  }
]
```

用户名大小写不敏感，密码大小写敏感。登录状态保存于 `anime_local_session`，只保存账号 ID 和用户名，不保存密码。

### 按账号隔离的数据

当前离线键改为以下形式：

```text
offline_<userId>_anime_tracker_data
offline_<userId>_anime_folders
offline_<userId>_anime_sources_v2
offline_<userId>_anime_search_history
offline_<userId>_anime_api_key
offline_<userId>_anime_api_provider
offline_<userId>_anime_api_url
```

主题和精简视图等纯界面偏好也使用同一账号前缀；后端地址和在线/离线模式开关仍是浏览器级设置，因为它们不属于某个账号。

未登录时继续使用单独的 `offline_guest_*` 键，避免覆盖已有离线数据。

## 交互和数据流

### 初始化

1. 页面从 `/api/config` 读取 Supabase 配置。
2. 有 Supabase 配置时，维持现有 Supabase Auth 流程。
3. 没有 Supabase 配置时，初始化本地认证模块，恢复 `anime_local_session`（如果存在）。
4. 根据当前账号刷新数据键，然后加载该账号的数据；没有账号时加载访客数据。
5. 离线模式下登录按钮始终可用，并显示“本地账号”。

### 注册

1. 用户输入用户名和至少 6 位密码，并确认密码。
2. 规范化用户名并检查重复。
3. 生成随机 salt，使用 PBKDF2-SHA-256 派生密码哈希。
4. 写入账号索引和当前会话。
5. 如果这是新账号且访客数据存在，提示用户是否迁移；确认后只在目标账号为空时迁移访客数据。
6. 刷新数据键和页面视图。

### 登录和切换

1. 用户输入用户名和密码。
2. 根据账号索引验证 PBKDF2 哈希。
3. 写入本地会话，切换数据键，清空旧账号的内存数据后加载新账号数据。
4. 已登录时点击账号按钮显示“切换账号”和“退出登录”。
5. 记住账号功能只保存用户名，不保存密码；切换时仍需输入密码。

### 退出

1. 清除当前会话。
2. 清空页面内存中的账号数据。
3. 切换回 `offline_guest_*` 键并刷新视图。
4. 不删除该账号的数据，重新登录后仍可恢复。

## 错误处理

- 用户名为空、格式不合法或密码少于 6 位时，在弹窗内直接提示。
- 注册同名账号时提示“账号已存在”。
- 登录失败统一提示“账号或密码错误”，不透露账号是否存在。
- 浏览器不支持 Web Crypto 或 `localStorage` 不可写时，提示用户使用正常浏览器窗口并检查站点存储权限。
- 存储空间不足时保留内存状态并提示导出数据，避免静默覆盖。
- Supabase 配置存在时不混用本地账号；在线/离线模式继续由现有模式切换控制。

## 安全边界

- 使用 PBKDF2 + 随机 salt，避免保存明文密码或可逆的 Base64 密码。
- 不在 URL、日志或导出文件中输出密码哈希以外的认证信息。
- 本地账号只用于同一浏览器内的便利性隔离，不等同于服务端安全认证。
- 现有的 Supabase `serviceRoleKey` 继续只保留在服务端配置中，不写入本地账号模块。

## 实现范围

- 新增 `js/local-auth.js`：本地账号存储、密码哈希、登录会话和认证状态。
- 修改 `index.html`：离线模式启用认证入口、按当前账号刷新本地数据键、处理登录/注册/退出/切换和迁移提示。
- 修改 `README.md`：增加离线账号的简短使用说明和数据清除限制。
- 不修改 `server.js`、`supabase-schema.sql` 或在线 Supabase 数据结构。

## 验证计划

- 本地认证模块测试：注册成功、重复用户名、正确密码登录、错误密码拒绝、注销和会话恢复。
- 浏览器手动验证：创建账号 A 添加番剧，退出；创建账号 B，确认看不到 A 的数据；重新登录 A，确认数据恢复。
- 迁移验证：已有访客数据注册第一个账号后，确认迁移后数据仍存在且只出现一次。
- 在线回归验证：配置 Supabase 时，现有在线登录和云端同步路径不受影响。
- 启动回归验证：`start.bat`、`npm start` 和 `http://localhost:3456/health` 继续正常。
